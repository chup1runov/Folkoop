# FOLKOOP Whole-System Visual Prototype v0.2

Date: 5 October 2026  
Status: visual/information-architecture lab; not production truth.

## Owner decision represented

The visual integration track now treats three ways of using FOLKOOP as equal:

1. **Look around / be among people** — community, conversations, meetings, learning and belonging without requiring a task.
2. **Solve a concrete question** — need, offer, resource, city route or local opportunity.
3. **Organise something together** — project, people, resources, tasks, economic coordination, decisions, logistics and outcome.

These are not three applications or registration modes. A person may move freely between them.

## Full integration scope kept in view

The lab keeps all ten components represented in a hidden design-only coverage map:

1. current FOLKOOP implementation base;
2. civic/public-infrastructure origin;
3. community/Center origin, online + physical/hybrid;
4. owner's cooperative social-network concept;
5. attributed external cooperative-economy research ideas;
6. ГБГ Форум;

10. blockchain.

The ordinary participant never sees these as ten product modules.

## v0.2 IA hypothesis

Global environments:
- My FOLKOOP;
- Together;
- City;
- Center;
- Messages.

Projects are deep contextual workspaces. They remain prominently reachable from My FOLKOOP and Together and may be pinned. They are not deleted.

A project workspace has a stable first layer:
- Overview;
- People;
- Work;
- Resources;
- More.

Deeper tools under More can include:
- Economy;
- Decisions/Agreements;
- Outcome/Evidence.

This is intended to avoid both extremes:
- one top-level tab for every domain object;
- constantly disappearing contextual navigation.

## Friendly interaction principles embodied by the lab

- start small;
- browse without commitment;
- asking is not joining;
- messaging is not task acceptance;
- linking a resource is not booking it;
- participant claim is not independent confirmation;
- future Host flow never pretends that a staffed Host is currently operating;
- planned blockchain/Web3/SDCF depth is expressed through human tasks rather than technology-first navigation.

## Three prototype journeys

### Simple
"Ladder on Saturday":
draft -> matches -> conversation -> optional return report.
No project is required.

### Social
Center:
ordinary community -> event -> optional participation.
No productivity requirement.

### Deep
Repair Day:
Center/community -> City/place option -> project workspace -> people/work/resources -> economy -> decision -> outcome/evidence.

The same object may be reachable from multiple appropriate locations without becoming multiple records.

## Design mode

A separate design mode exposes:
- the ten-source coverage map;
- implementation/prototype/planned status notes.

Normal user mode hides this architecture metadata.

## Truth boundary

All interactions in v0.2 are local visual prototype state only. They do not:
- publish to Supabase;
- contact a Host;
- book a place;
- copy forum data;
- send an official city action;
- create a legal agreement;
- perform a blockchain transaction.

## Promotion rule

No v0.2 IA choice moves to the production shell solely because it looks good. The owner first reviews the visual model. Accepted patterns then require a production mapping, permissions/privacy review, migration/API plan where needed, regression coverage and appropriate user evidence.
