## A10 — Post-pilot decision gate

- weak Match -> discovery/local density;
- weak Commit -> trust/relevance/commitment;
- weak Coordinate -> workspace/logistics;
- weak Act -> offline/logistics/place barriers;
- unclear Outcome -> structured outcome/attestation;
- weak Repeat -> belonging/recurring value.

The next major engineering slice must correspond to the measured failure.

# PROGRAM C — POST-PILOT BOTTLENECK PROJECTS

## C01 — Local Density & Discovery

Trigger: genuine intents exist but useful matches are weak.

Possible work:

- explainable discovery;
- derived Action Graph only if cross-domain querying becomes the real constraint.

## C02 — Commitment & Contextual Trust

Trigger: relevant matches are found but participants do not commit.

Possible work:
- clearer expectations;
- roles;
- availability;
- contextual evidence;
- participant history;
- no universal scalar trust score.

## C03 — Cooperation Workspace

Trigger: people join but coordination frequently leaves FOLKOOP or fails.

Possible work:
- tasks;
- lightweight scheduling;
- reminders;
- better work-chat/inbox;
- realtime only if needed.

## C04 — Offline Action

Trigger: coordination occurs but useful real-world action does not.

Investigate non-software causes first:
- distance;
- timing;
- trust;
- transport;
- tools;
- venue;
- responsibility.

Only introduce Place/Activity/Host infrastructure if evidence points there.

## C05 — Structured Outcome & Attestation

Trigger: real actions happen but the system cannot represent outcomes truthfully enough.

Candidate:
- `fk_outcomes`;
- participant confirmations;
- evidence metadata;
- provenance journal;
- no blockchain requirement.

## C06 — Repeat & Belonging

Trigger: useful outcomes happen but repeat cooperation is weak.

Possible work:
- recurring opportunities;
- Meetup/Activity;
- newcomer flow;
- community continuity;
- controllable reminders/digests.

No streaks or compulsive engagement mechanics.

# 6. Definition of project discipline

A mini-project is complete only when:

1. its trigger/problem is explicit;
2. implementation or operational work is finished;
3. relevant automated/manual verification passes;
4. docs reflect current reality;
5. no stronger claim is made than the evidence supports;
6. the next dependency is unblocked or explicitly documented.

The purpose of this plan is to make FOLKOOP easier to execute, not to create a larger backlog.
