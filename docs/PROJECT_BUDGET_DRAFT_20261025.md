# Вклады и бюджет проекта

25 октября 2026. Статус: локальный непроверенный код. Миграция не применена,
сборка, тесты, браузерные и SQL-проверки не запускались. Не опубликовано.

## Основание и границы

Владелец явно выбрал: каждый сам обещает вклад; получение подтверждается отдельно;
деньги отдельно от вещей и времени. Это наша адаптация требований Charter §6 и
[сохранённого разбора Токаренко](research/sources/TOKARENKO_KOOPSET_RESEARCH.md),
не прямая цитата из заново просмотренной презентации.

Существующие Economic Flow / роли и закупки сохранены. Новый учёт прикреплён
к тому же проекту и не заменяет их. Не создаёт кошелёк, переводы, банковский баланс,
регулируемый бухгалтерский учёт, задолженности, платёжные обязательства или рейтинг людей.

## Что написано

- Организатор создаёт неизменяемые строки потребностей: название, тип, количество.
  Типы: деньги в SEK, вещи в штуках, время в часах, помещение в часах.
  Участник сам создаёт обещание на конкретную потребность. Чужой ID вкладчика API
  не принимает: автор определяется сервером по сессии.
- Состояния: `promised → submitted → received`. Отметка «я передал / выполнил»
  не увеличивает полученное до отдельного подтверждения.
- Обычный вклад подтверждает текущий организатор. Вклад самого организатора
  подтверждает другой текущий участник проекта; самоподтверждение запрещено.
  Это человеческое подтверждение, не независимая финансовая экспертиза.
- До получения автор может отозвать обещание. Проверяющий может вернуть
  `submitted → promised` с причиной; отменить ошибочное подтверждение
  `received → submitted` с причиной. История сохраняет исходное подтверждение.
- Частичную передачу пока оформляют отдельными обещаниями. Количество существующего
  обещания не редактируется за спиной автора: отзыв и новое личное обещание.
- Потребность можно отменить только когда нет неотозванных вкладов и неаннулированных
  расходов. Изменение плана — отмена допустимой старой строки и создание новой,
  а не перенос обещаний на другие условия.
- Организатор записывает расход по денежной строке с описанием. Это заявление
  организатора, без автоматического доказательства платежа. Исправление — аннулировать
  с причиной и добавить новую запись; исходная строка/история остаются.
- UI показывает кто обещал, статус и количество; после получения — кто подтвердил
  и когда. Журнал показывает действия, автора, дату, потребность и причины исправлений.
- При закрытом проекте всё доступно только для чтения. При отсутствии/ошибке/устаревании
  снимка нет ложного нулевого бюджета и форм действий. Свежесть проверяется при рендере
  (60 секунд), без фонового таймера; сервер повторно проверяет права и ревизию.

## Расчёты

Все значения хранятся целыми сотыми: öre, сотые часа, 100 на одну штуку.
Вещи допускают только целое число штук. Для денег нет двоичной арифметики дробных
крон в суммировании. Один ввод: 0,01–1 000 000 единиц, вещи от 1 штуки.

Для каждой строки:

- обещано всего = сумма всех вкладов кроме отозванных, включая уже полученные;
- передано, ждёт подтверждения = сумма `submitted`;
- получено = сумма `received`;
- не покрыто обещаниями = `max(нужно − обещано всего, 0)`;
- ещё получить = `max(нужно − получено, 0)`;
- избытки обещанного и полученного показаны отдельно, не как отрицательный дефицит.

Общий денежный блок суммирует только SEK: план расходов, обещания, подтверждённое
получение, дефициты по целевым строкам, расходы без аннулированных записей,
расчётный остаток `получено − записанные расходы`. Он может быть отрицательным;
это не скрывается и не означает банковский овердрафт. Обещания целевые: лишние деньги
на чай автоматически не покрывают обещание на материалы. Часы помещения не складываются
с часами ведущего; вещи не переводятся в денежную стоимость. Внешние платежи не проверяются.

## Пример практики шведского

В UI есть раскрываемый явно вымышленный пример, в том числе в проекте встречи Муры:

| Потребность | Нужно | Состояние примера |
|---|---:|---|
| Чай | 150 SEK | A передал 100 SEK, B подтвердил |
| Материалы | 50 SEK | B обещал 50 SEK |
| Помещение | 2 часа | C сообщил о предоставлении, подтверждения ещё нет |
| Ведение встречи | 2 часа | Пока никто не обещал |

План — 200 SEK, обещано всего — 150, получено — 100, без обещаний — 50,
ещё получить — 100. Вымышленный расход на чай — 30, расчётный остаток — 70 SEK.
Это ожидаемые арифметические значения примера, **не результат запуска теста**.
Пример ничего не записывает в базу и не создаёт реальных участников/вкладов.
Для реального проекта организатор создаёт строки вручную, люди лично обещают.

- [network-budget.js](../apps/web/network-budget.js): `amount`, `totals`, `render`,
  read-only пример, формы, черновики строк на 11 языках (без человеческого одобрения).
- [network-client.js](../apps/web/network-client.js): `projectBudget`, `budgetAction`,
  четыре дополнительные коллекции ограниченной личной выгрузки.
- [network-ui.js](../apps/web/network-ui.js): загрузка, карточка проекта и обработчики;
  формы/ID запросов только в памяти, очищаются при смене Auth.
- [Миграция](../supabase/migrations/20261025191414_project_contributions_budget.sql):
  `fk_project_budget_needs`, `fk_project_contributions`, `fk_project_expenses`,
  `fk_project_budget_events`; RPC action/snapshot; inventory v16.
- Подключения в `folkoop.html`, BUILD_FILES/PRECACHE_PATHS, CSS; allowlist приватных
  RPC в SQL security test дополнен, сам тест не запускался.

Чтение — действующая сессия и членство проекта. Прямые клиентские записи запрещены;
приватные definer-функции с пустым search_path и проверками действующего участника,
публичные invoker-обёртки. Записи сериализуются блокировкой проекта; состояния вкладов
проверяются по revision. UUID команды обеспечивает идемпотентность неизменённого
запроса, пока UI сохраняет его в памяти. После полной перезагрузки вкладки неопределённый
исход отправки нужно сверить с историей перед новым обещанием/расходом.

Лимиты на проект: 100 потребностей, 500 вкладов, 500 расходов, 5000 событий,
включая отменённые. Полный ограниченный снимок через один RPC, без молчаливого
обрезания сумм из-за лимита REST rows. После достижения лимита нужны операторский
разбор и развитие пагинации/архива, а не удаление истории для обхода лимита.

Удаление Auth обнуляет ссылки на автора/подтверждающего, не удаляя общие суммы.
Тексты и события требуют отдельного privacy review: null ссылки не доказывают
анонимность. Выход/удаление участника сохраняет общую историю, но прекращает доступ.
Удаление самого проекта каскадное, как в существующей модели; это не вечный аудит.
