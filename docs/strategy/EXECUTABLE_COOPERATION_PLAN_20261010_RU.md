Дата: **10 октября 2026**. Версия: **1.0**.
Статус: **стратегическая программа одобрена владельцем; реализация поэтапная, с отдельными review/acceptance gates**.
Главное исследование: [EXECUTABLE_COOPERATION_VISION_20261010_RU.md](EXECUTABLE_COOPERATION_VISION_20261010_RU.md).
Контролирующие приоритеты: ../FOUNDATION_CHARTER.md; ../MASTER_PLAN_20261004.md; ../GOTEBORG_CORE_LOOP_PILOT.md; ../NO_LOSS_REQUIREMENTS_REGISTER.json.
Программа **НЕ заменяет текущий master plan**, не отменяет P0/pre-pilot работы, не разрешает автоматически новые GitHub merges, production migrations, real-user uploads, external costs, LLM data transfer или mainnet.

## 0. Результат, ради которого пишется код

FOLKOOP должен превращать человеческую цель в **реально осуществимый и согласованный** совместный план, а затем честно отличать **запланировано / предложено / условно согласовано / подтверждено / зарезервировано / исполнено / заявлено участником / подтверждено другой стороной / имеется внешнее свидетельство / проверена целостность документа**.

**Definition of program success** (не обещание и не метрика отчётности до пилота):
1. Человек самостоятельно начинает простое действие и возвращается к тому же объекту и разговору без дублирования записей.
2. Для составного дела группа видит минимум два объяснимых варианта или обоснованное отсутствие выполнимого варианта.
3. Каждая сторона понимает условия, может отказаться, а существенные изменения требуют нового согласия.
4. Отказ, пропущенный срок, конфликт ресурсов и отмена видны в истории; никакой «зелёный Done» не скрывает несостоявшуюся работу.
5. Реальный Outcome, участникское заявление, независимое подтверждение и integrity-proof остаются разными понятиями.
6. Показан межорганизационный сценарий, где партнёр не обязан отдавать FOLKOOP свою базу.
7. Проверяемая квитанция о версии соглашения остаётся проверяемой третьей стороной без доступа к админке FOLKOOP.
8. Измерено, стало ли полезное взаимодействие меньше требовать времени/усилий относительно Telegram + таблица + звонки.

**Переход к следующей фазе определяет evidence, а не календарь.** Целевые значения измерений задаются и фиксируются до эксперимента; предложенное сокращение координационного времени примерно на 50% — исследовательская амбиция, не прогноз.

## 4. Этап ECX-1 — «есть» ещё не означает «доступно» (Capability Truth / R1–R2)

**Зависимость:** ECX-0 и реальные тестовые аккаунты для hosted gate там, где нужен runtime.

**Вертикальный срез:** Project говорит «нужен инструмент в субботу» → видит имеющиеся записи Resource → делает явный запрос владельцу → получает добровольный ответ с условиями и сроком. Не объявлять запрос резервом.

**Существующие опоры:** R1 Project Requirement + owner-private Resource Availability, E01/Shared Purchase, будущий R2 Offer. Не создавать параллельную таблицу «resources_v2» ради этого плана.

**Кандидатский контракт** (не SQL-миграция): stable resource/object ID; capability/source/actor; time windows + timezone; quantity/unit/capacity; eligibility; location scope; last_confirmed/expiry; proposed terms; visibility; status and revocation. Unknown vs false; self-asserted vs verified.

**Тесты:** конфликтующие временные интервалы, незаданная единица, устаревшая доступность, неучастник, владелец удалил ресурс, отмена запроса, двойное подтверждение, отсутствие персональных утечек через поиск.

**Done:** конкретный пользовательский запрос и ответ работают с нормальной авторизацией и отказами; отрицательные сценарии проходят; когда private feature OFF, нет ложных affordances или обещаний.

**Не включать:** реальное бронирование, оплату, автоматические обязательства и псевдопроверенную доступность.

## 5. Этап ECX-2 — объяснимое составление вариантов (Feasibility Planner v0)

**Зависимость:** достаточные типизированные inputs ECX-1; P0 безопасности не обходится.

**Начать без ИИ.** Из 1–2 Resource и 2–3 реальных условий собрать детерминированные варианты через обычные правила: пересечение дат, роли, вместимость, совместимость и provenance. При недостатке фактов выводить «неизвестно» и вопросы человеку.

Затем лабораторный constraint solver (OR-Tools либо эквивалент только после оценки зависимости), который выдаёт:
- feasible/infeasible/unknown для каждого варианта;
- violated constraints и unmet prerequisites;
- объяснимые альтернативы (дата, место, транспорт);
- оценочные критерии с диапазонами и источниками, а не ложную вероятность успеха.

**Тесты:** ноль вариантов, равноправные альтернативы, contradictory constraints, отсутствие ответа партнёра, нехватка ресурса, устаревшее расписание, приватные навыки, конфликт ролей. Решатель не использует незаявленную чувствительную характеристику.

**Done:** при фиксированном наборе входов результат воспроизводим; причины недостижимости понятны человеку; нет automatic booking/publishing.

## 6. Этап ECX-3 — Conditional Commitments / versioned consent

**Зависимость:** ECX-1 + выбор варианта ECX-2; можно проектировать design-only раньше.

**Вертикальный сценарий:** «Могу привезти станок после 17:00, если указан ответственный за возврат» → другая сторона принимает именно эти условия → изменение времени отзывается/требует re-consent → если отказ, автоматический статус проекта НЕ становится завершённым.

**Кандидатская модель:** condition_id, author, source_object, proposal_version, binding_scope, conditions, expires_at, position (interest / conditional / accepted / withdrawn / expired), explicit confirmation, provenance, supersession/corrections, visible affected parties. Юридическую квалификацию каждого типа согласия обсуждать отдельно; не назвать любое подтверждение legally binding agreement.

**Тесты:** race two acceptors, expired proposal, owner/membership changes, cancel/refund boundary, stale client, repeated request idempotency, material term changes, partial federation failure, blocked user. SQL transaction работает внутри одного store, а физическая/межорганизационная операция компенсируется или отменяется явным процессом.

**Done:** никакого переноса согласия на существенно новую версию; отзыв/изменение виден сторонам; RLS и права на действие доказаны.

## 7. Этап ECX-4 — исполнение, ошибки и честный Outcome / Evidence

**Зависимость:** ECX-3 или доказанный реальный сценарий, где действия требуют независимых подтверждений.

**Вертикальный сценарий:** план включает передачу и возврат ресурса; отмена транспорта влечёт пересмотр плана; передача и возврат подтверждаются вовлечёнными сторонами, исходные объявления и чат остаются теми же.

Сохраняем различие:
- plan/assigned/ready;
- preliminary/confirmed reservation;
- execution status;
- participant claimed;
- counterparty confirmed;
- external evidence referenced;
- integrity proof;
- disputed/withdrawn/unclear.

Переиспользовать Shared Purchase delivery/pickup как authoritative для purchase-kind; generic E02 fulfilment только для оправданных Project-owned flows, пока bridge не согласован. Outcome не выводится автоматически из закрытого Economic Flow. Использовать уже принятый Outcome Integrity contract.

**Тесты:** false completion, missing proof, conflicting accounts, report withdrawal, evidence retention, private document leak, correction without rewriting original claim, closure/deletion semantics.

**Done:** фактическая история изменений не теряется, а человек не видит «доказано» после одного клика Done.

## 8. Этап ECX-5 — ИИ с ограниченным поручением (READ → DRAFT → COMMIT)

**Разрешение на implementation отдельно.** Лабораторные прототипы можно делать параллельно ECX-2 без доступа к реальным приватным данным.

**Первый use case:** по явно выбранному Project, разрешённым данным и цельному source bundle ИИ готовит варианты и *черновик* сообщения. Никаких автоматических контактов, покупок или резервов.

**Контракт:** principal identity; purpose; read scopes; authorized tool list; target objects; data minimization; token/usage budget; message cap; expiry; revocation; model/provider/version; recommendation provenance; approval receipt bound to exact payload for any later COMMIT.

MCP/A2A — транспорт/интероперабельность, не права; все действия через тот же RLS/RPC/security gate, что человек. Не выдавать API ключи провайдера клиенту. Prompt injection из чатов/описаний/источников — недоверенный ввод, не системная инструкция. Никакой сервисной SQL-роли у агента.

**Оценивание:** извлечение целей/сроков/условий на 11 языках и RTL; ложные обещания; пропущенные ограничения; hallucinated partners; различение запроса и обязательства; source attribution; human satisfaction; latency; стоимость; действия после отзыва. Сравнение с детерминированным ECX-2.

**Done:** агент безопасно получает доступ только к разрешённому контексту, умеет объяснить, чего не знает, не делает никаких COMMIT без точного подтверждения. Live enablement только после отдельного privacy/DPA/cost decision.

## 9. Этап ECX-6 — одно реальное межсистемное взаимодействие

**Зависимость:** стабильный объектный контракт ECX-1 и видимость ошибок/согласий ECX-3–4, хотя design adaptation можно вести заранее.

Найти **одного согласного партнёра** (площадка, организация, community provider). Первые операции: publish/read opted-in capability → request terms → explicit partner response → cancellation/expiry. Доказать авторизацию, provenance, несовпадение источников и отказ сети.

Выбрать только реально нужный адаптер:
- HSDS/Open Referral для service, organisation, location and accessibility directory;
- Valueflows alignment для resource/event/commitment semantics;
- Beckn для зрелого independent discovery-to-fulfilment protocol, если оправдано;
- ActivityPub только opt-in public-social announcements;
- MCP/A2A только если партнёр действительно использует agent tools.

**Тесты:** объект из другой системы не становится локальной authoritative записью; actor/issuer verified separately; remote revocation; stale cache; duplicate/replay delivery; partner unavailable; access policy mismatches; no personal data by default.

**Done:** обе стороны могут независимо подтвердить состояние и исправление; пользователь не видит «забронировано» до точного подтверждения партнёра.

## 10. Этап ECX-7 — scoped blockchain proof (testnet only)

**Зависимость:** versioned Agreement/Decision и typed Outcome/Evidence семантика; не запускать mainnet без owner approval.

**Проверяемая задача:** две независимые организации подписали версию соглашения; появляется новая версия/отзыв; третья сторона проверяет историю и факт закрепления, не обращаясь к БД администратора FOLKOOP.

**Сравнить**:
A. подписанный off-chain record + внешняя trusted timestamp;
B. Merkle commitment в выбранной testnet с independently verifiable transaction proof.

Проверять собственные ключи сторон или выбранную управляемую модель с явно разобранной независимостью; полностью публичная цепочка не принимает PII, project IDs и predictable personal hashes. Сохранять receipt, key lifecycle, revocation/dispute version, chain outage/reorg/finality и внешний verification CLI.

**Тесты:** изменённая версия не проходит; отозванный signer не объявляется действующим без проверки; offline verification; chain unavailable; correlation/privacy; replay; proof revoked but history retained; real-world Outcome остаётся отдельным.

**Done:** независимый проверяющий воспроизводит proof и его ограничения; отдельно принято решение, действительно ли blockchain даёт пользу сверх signed records. **Это не autorização public mainnet, fee spend, wallet, token, DAO или KYC.**

## 11. Этап ECX-8 — переносимые практики и добровольный объединённый спрос

**Зависимость:** реальные истории ECX-4 с согласиями и допустимой публикацией; нельзя обучаться на приватных чатах без отдельного разрешения.

Две функции:
- recipe/cookbook: роль, варианты, ресурсы, ограничения, failures, подтверждённые outcomes с указанием области применимости;
- unmet-demand: несколько явно разрешённых намерений → защищённая агрегированная заявка → предложенная организациям новая возможность (только after opt-in and privacy checks).

**Тесты:** малые группы не раскрываются; sensitive need ignored by default; false aggregate threshold, unmatched group, withdrawal, right to correction/deletion, insufficient sample, source-quality and provenance; шаблон не превращается в директиву «это всегда работает».

**Done:** другая команда использует recipe для действительного нового дела, а инициатор понимает его происхождение и ограничения. Отдельно измерять, появилась ли возможность, которой раньше не было.

## 12. Сквозной пример для end-to-end acceptance

**Repair Day:**
1. Человек/Center запускает идею без обязательного Project для любого посетителя.
2. Организатор осознанно создаёт существующий Project и контекстный work chat.
3. Требования к месту, 2 инструментам, человеку и транспорту фиксируются в R1.
4. ECX-1 показывает доступные объявления, но ещё не утверждает резерв.
5. ECX-2 предлагает варианты и показывает конфликт дат/недостающую роль.
6. ECX-3 получает условные согласия на конкретную версию.
7. При отмене перевозки план переоценивается; затронутые стороны явно подтверждают новую версию.
8. ECX-4 сохраняет выполнение и отдельно разные подтверждения результата/возврата.
9. ECX-5 AI (если добровольно разрешён) помогает составить варианты и сообщения, но не утверждает их.
10. ECX-6 партнёр обменивается одним выбранным сообщением, не выгружая свою внутреннюю базу.
11. ECX-7 при необходимости проверяет версию межорганизационного соглашения.
12. ECX-8 переносит обезличенную, разрешённую практику в другой local Node.

**Отрицательные сценарии обязательны:** никто не ответил; координатор заболел; владелец отозвал ресурс; помещение недоступно; источники противоречат; пользователь удалил аккаунт; AI предложил недостоверный ресурс; внешняя сеть упала; сторона оспаривает Outcome.

## 14. План исследований и измерения результата

Перед экспериментом фиксировать сценарий, среду, целевую группу и базовую альтернативу. Сопоставлять похожие реальные дела, а не выбирать самые успешные кейсы FOLKOOP против худших сторон мессенджера.

Метрики:
- первичное понимание продукта — независимые ответы свежих участников;
- время и число человеческих контактов до полезного подтверждения;
- median organiser minutes per completed coordination (включая Hosts);
- доля планов с unmet prerequisites и объяснимой причиной;
- проценты cancelled / disputed / unknown outcomes;
- доля независимых, а не operator-facilitated matches;
- добровольные повторные кооперации и отдельная social/belonging оценка;
- доступность/актуальность каталога; partner latency/failures;
- AI errors, latency, cost, privacy incidents;
- случаи **действительно созданной** возможности, которой не было раньше;
- экологическая польза только с прозрачным physical baseline и logistics overhead.

**Пример желаемого эффекта для проверки**: существенное снижение нагрузки координатора, ориентир около 50% относительно обычного способа. Не говорить, что это уже достигнуто или причинно доказано на малых выборках.

Acceptance evidence: issue/pr → review → exact head CI → disposable/security QA → отдельный hosted gate (если требуется) → real-user observation → independent outcome confirmation → follow-up. Никогда не считать один зелёный тест доказательством общественного воздействия.
