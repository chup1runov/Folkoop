# Взять задачу → выполнить → подтвердить результат

18 октября 2026. **Локальный код, не проверен, не опубликован.**
Продолжение [решений и задач](PROJECT_DECISIONS_DRAFT_20261018.md).
Проверки отложены по прямому указанию владельца; миграция не применялась.

## Поведение

Новые задачи, в том числе созданные из решения, получают отдельный рабочий цикл:

`available → working → submitted → verified`

Проверяющий может вернуть `submitted → changes`; исполнитель снова сдаёт результат
через `changes → submitted`. Из `working` и `changes` исполнитель может отказаться:
задача становится свободной, текущие поля результата очищаются, история остаётся.

- «Предложить исполнителя» — только предложение. Лишь этот участник может принять
  адресованную ему задачу; свободную может взять любой текущий участник проекта.
- Для сдачи нужен текст результата, 2–2000 символов. Файлы и внешние доказательства
  пока не добавляются. Текст не исполняется как HTML.
- До отдельного подтверждения обычный `status` остаётся `doing`, а не `done`.
- Проверяет текущий организатор. Если задачу выполнил сам организатор, результат
  может подтвердить другой текущий участник. Самоподтверждение запрещено.
  Это правило первой версии; выделенная роль проверяющего пока не реализована.
- Возврат требует пояснения, 2–1000 символов. Подтверждение допускает комментарий.
- Подтверждение относится к текущей сдаче. После доработки нужна новая проверка.
- Все действия требуют активного проекта, членства и действующей пилотной сессии.
- Блокировка строки и ожидаемая ревизия защищают от конкурирующих переходов.
  Повтор с устаревшей ревизией даёт конфликт и обновление UI, не второй переход.
- Старые RPC изменения статуса не обходят новый цикл. Назначение после принятия
  запрещено; до принятия остаётся предложением и повышает ревизию.
- Завершённый результат здесь не переоткрывается. Исправления после подтверждения,
  споры и особые права проверяющего остаются отдельным следующим шагом.

## Совместимость и данные

Существующие на момент миграции задачи получают `work_stage=legacy`: старое `done`
не объявляется результатом с чужим подтверждением. Их старые действия сохранены.
Для новых строк default — `available`. Существующие задачи не конвертируются сами.

`fk_task_work_events` сохраняет автора, действие, ревизию, время и пояснение каждой
сдачи/проверки. Новые таблицы доступны участникам проекта на чтение по RLS;
клиентская запись только через RPC. Это история действий, не неизменяемый реестр
и не независимое доказательство события. Удаление задачи удаляет её историю
каскадом; прежнее право удаления сохранено. Отдельного просмотра всей истории
в карточке пока нет: UI показывает последнее состояние, результат и проверку.

Черновик пояснения остаётся в памяти при ошибке, сбрасывается при смене аккаунта.
Выгрузка теперь содержит 23 коллекции, включая свои task-work события; круг задач
расширен до созданных, назначенных себе и проверенных собой. Ограничения выгрузки
по доступу/лимитам сохраняются. Для оператора добавлена inventory v5 поверх v4.

11 языков имеют черновые строки, но языковая и техническая приёмка не проводилась.
Мура в проекте встречи на шведском объясняет связь «взяла карточки → подготовила →
другой человек подтвердил». Это иллюстрация, не запись реального события.

## Следующая отложенная приёмка

1. Синтаксис JS/SQL, сборка, права функций/RLS; обновить export fixtures на 23 коллекции.
2. Два участника одновременно берут одну свободную задачу: принимает только один.
3. Предложение чужой роли не считается принятием; нельзя принять за другого.
4. Исполнитель сдаёт результат, организатор возвращает с причиной, исполнитель
   сдаёт снова, организатор подтверждает именно последнюю ревизию.
5. Работа организатора подтверждается другим участником; никто не подтверждает себя.
6. Пустой результат/причина, XSS, превышение длины, устаревшая вкладка, повтор после
   потери ответа, отозванная сессия и выход из проекта, закрытый проект.
7. Попытка обойти цикл через старые status/assign RPC; сохранность legacy поведения.
8. Экспорт, privacy inventory, отдельное закрытие тестового аккаунта, сохранность чужих задач.
9. Мобильный/клавиатурный UI, RTL и все локали, история решений и статусы задач.

Клиент нельзя публиковать перед миграцией: новые поля/таблица нужны для выгрузки.
Никакой из перечисленных пунктов в этом шаге не запускался.
